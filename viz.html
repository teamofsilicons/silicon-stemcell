Silicon Stemcell

An autonomous manager → worker agent runtime. Glass is the cloud authority, Silicon Interface is the messaging transport, main.py is a single long-lived Python process holding an event loop, and every real unit of work is a separate LLM CLI subprocess. Read from the outside in.

Glass (cloud authority) Silicon Interface (transport) Stemcell core (this repo) Manager (persistent LLM session) Worker (ephemeral LLM subprocess)

Tick mechanics

wait_for_runtime_activity(timeout) maintenance tick fence? schedule.due(now, activity) run_event_loop_tick(selected) merge → context_by_carbon dispatcher.submit()
next tick — timeout = min(next due, contact integrity, inactive-call deadline, 60s or 0.5s)
backpressure

A raised exception increments failure_count and pushes failure_not_before out by 2^n, capped at 30 s — a crash can never become a hot retry loop.

maintenance fence

While maintenance is active only check_interface, check_manager_messages, and check_workers are eligible. New roots stay durably queued.

integrity

validate_contacts_integrity() runs every 300 s + a hash-derived 0–60 s offset so fleet instances never sync up.

03Dispatcher and one manager turn

ManagerDispatcher guarantees: serialized per contact, parallel across contacts. A new message for a busy contact is coalesced into that contact's next turn; a message for another contact starts its own thread immediately. Bounded at 16 concurrent contacts.

inbound context durable MAINTENANCE.enqueue_root() admission _pending[contact] thread manager-dispatch-<id> lease + heartbeat run_all_managers() complete_roots()
on exception → retry_roots() puts the same context back, same marker, no loss

Inside run_all_managers — acting mid-run

A manager no longer returns a batch of tool JSON for the Stemcell to execute after the turn. It runs iwantto as a shell command while the turn is running, the command executes immediately, and the result comes straight back on stdout. So a manager can send a message, read the reply, and act on it inside a single turn.

issue_run_env() → actor token get_manager_prompt(carbon_id) provider streams mid-run iwantto send / work / delegate … executes now, prints result
the manager reads stdout and keeps going — no round-trip through the Stemcell
how the turn ends

The Stemcell never sees the actions, only that the turn finished. What tells it whether the manager did anything is the run record iwantto writes as it goes (core/iwantto/journal.py, keyed by the actor token). acted or do-nothing → the turn is complete. nothing at all → re-prompted, because running at least one command every turn is mandatory. Rate limit → lifecycle deferred. Timeout → 1 retry, then paused. Budget exhausted at 10 iterations → work paused.

identity

The token is issued per turn into the provider subprocess's own environment — never os.environ, because managers run concurrently in threads. It resolves iwantto's "I", and stops resolving the moment the turn ends. Tool JSON is still parsed and executed, but only so injected provider-error replies keep working.

04iwantto — the complete command surface

One CLI, used by managers, advisors, and workers alike. Identity decides what each command means. A message goes out directly only when it is run by that contact's own manager — every other case is routed to the target's manager, so a contact only ever hears one voice and no two managers ask them the same question twice. An advisor shares its manager's "I" and so shares that reach; a worker never does, even toward its own manager's Carbon. Implemented in core/iwantto/; installed to <data root>/.local/bin/iwantto on every boot, which is already first on PATH.

Identity, not flags. Every run the Stemcell spawns is registered in core/iwantto/actor.py and handed a token in its environment. iwantto resolves that token back to a manager, advisor, or worker — a stale or copied variable cannot name an actor it was never issued for, and a parent's token is stripped before a child is spawned so a manager's identity never leaks into its worker.

Boundary rule enforced in prompt, not code: a manager may never read another manager's workers, sessions, archives, or memory. Routing through the target's manager is the only cross-contact channel, and any claim attributed to a carbon must carry that carbon's verbatim message as a labeled quote.

Setup questions come last on purpose. Every trigger — message, heartbeat, cron, another manager — walks the tree in prompts/SETUP_QUESTIONS.py before anything is done. Running commands during that phase is forbidden: it is for thinking. Answers can pull in GIVE_UPDATES.md, NONCARBON_COMMS.md, or BE_PROACTIVE.md. So the shape of a trigger is msg → setup questions → work → done.
